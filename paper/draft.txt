Abstract :
    LLM agents now operate as a privileged application layer on a user's machine, with access to mail, files, code, calendars and MCP-connected external tools, yet they have no built-in mechanism to verify that the person typing into an already-signed-in session is still the legitimate user. This identity gap aligns with OWASP risks (LLM06: Excessive Agency, Agentic ASI03: Identity and Privilege Abuse) and with NIST guidance on digital identity and AI risk management, but the empirical question of whether it is closable from user text alone is largely open. We build a profile-query authorship verification benchmark on WildChat-1M, a public dataset of real user-LLM conversations, and PAN-20 regrouped at the author level, with author-disjoint 60/20/20 split repeated across three seeds and a 70/30 per-user profile-query split. We train contrastive bi-encoders with triplet margin loss on four transformer backbones (DistilBERT, BERT-base, MiniLM-L6 and ELECTRA-base) under two training regimes, 100% random imposters and a 50/30/20 mix of random, semi-hard and hard imposters mined by TF-IDF over character and word n-grams. Models trained on random imposters exceed 0.9 ROC-AUC against random imposters but drop by around 10 AUC points on WildChat against topic-similar imposters, suggesting they rely on topic and vocabulary rather than writing style alone. Hardness-aware training closes most of the robustness gap on WildChat and a substantial part on PAN, lifting TAR@FAR=1% on WildChat Hard from around 6-7% to 20-22% for BERT and DistilBERT with a median messages-to-detect of one, and we observe the same direction under a secondary SBERT hardness miner on WildChat. We release the benchmark construction scripts and evaluation code.

Introduction :
    LLM agents are quietly becoming one of the most privileged pieces of software on a user's machine. With protocols like Model Context Protocol (Anthropic, 2024) an agent can be connected to tools that send the user's mail, push commits, edit files in the user's workspace and run a shell command, all on the basis of a few words typed into a chat box. This is genuinely useful when the person typing is the user, but it becomes a serious problem the moment somebody else is typing. A roommate or coworker who borrowed the laptop, a friend who is "just checking one thing", an attacker who picked up an unlocked machine, all of them can sit in front of an already-signed-in agent and ask it for the same things the legitimate user could ask for. The agent has no built-in way to tell that the person at the keyboard is not the one who enrolled it.
    Many surrounding layers already perform some form of identity or authorization check: the operating system authenticates the user at login or unlock, MFA may be required for sensitive services, and browser or OAuth tokens authorize access to external applications. The LLM agent layer, however, usually has no equivalent check once a session is already open. The security community has identified related risks: the OWASP Top 10 for LLM Applications (2025) lists LLM06: Excessive Agency, the OWASP Top 10 for Agentic Applications (2026) identifies ASI03: Identity and Privilege Abuse, MITRE ATT&CK lists Impersonation (T1656) as an established adversary technique, and NIST's AI Risk Management Framework (NIST AI 100-1) emphasizes governance and accountability for AI systems. These frameworks motivate the risk, but they do not answer whether the problem is technically solvable at the agent layer using only the signal the agent reliably has: the text the user has typed. That is the question this paper sets out to answer, along with how many incoming messages such a verifier needs before it can make a reliable verification decision.
    The natural tool for this setting is a text encoder. The user has a profile of past messages; when a new message arrives, the encoder embeds the profile messages and the incoming query, pools them into profile and query vectors, and uses a cosine score to estimate whether they were written by the same user. We instantiate this idea with a contrastive bi-encoder trained using triplet margin loss. The model performs very well when the imposter is a uniformly random other user: on the random test regime, ROC-AUC rises above 0.9 even for MiniLM-L6, a 22.7M-parameter encoder. At first glance, the problem appears close to solved.
    But a uniformly random imposter is not the hardest adversary an LLM agent may face. A real imposter may share a workplace, family, or social circle with the user; they may know the same projects, codebases, or clients; and the topics they type about may overlap heavily with the genuine user's topics. When we replace the random imposter with another real user mined for topical similarity using TF-IDF over character and word n-grams, performance drops sharply: on WildChat, ROC-AUC falls by about 10 points on the hardest 5% of imposters for several encoders. The model that looked excellent on random imposters becomes much less reliable against topic-similar imposters, suggesting that it relies partly on topic and vocabulary rather than writing style alone. This topic-vs-style gap is the empirical core of the paper.
    Because the failure mode is security-relevant, we evaluate at security operating points rather than relying only on ROC-AUC. We report TAR@FAR=1%, the fraction of genuine users accepted when the false-accept rate for imposters is fixed at 1%, along with FAR@FRR=1%, the fraction of imposters accepted when the false-reject rate for genuine users is fixed at 1%. We also report EER, the robustness gap between random and hard imposters, and streaming metrics over the first three query messages, including imposter catch rate at three messages and median messages-to-detect. The full list of metrics and their security interpretation is given in Section 5. Our headline finding is that replacing purely random training negatives with a 50/30/20 mix of random, semi-hard, and hard imposters substantially reduces the random-to-hard robustness gap, especially on WildChat. On the WildChat Hard regime, TAR@FAR=1% rises from 6-7% under random-only training to 20-22% under hardness-aware training for BERT and DistilBERT, while the median messages-to-detect remains one.
    To simulate a deployment in which an agent has access to a user's past chat history and must verify fresh incoming messages, we build a profile-query benchmark from two datasets. WildChat-1M (Zhao et al., 2024), a public release of real user-LLM conversations, is our primary dataset because it best matches the agent-chat setting we study. PAN-20 is our secondary dataset: it is a standard authorship-verification benchmark, but because it is released in pairwise form, we regroup its texts at the author level to create user-like profiles. For both datasets, we use author-disjoint stratified 60/20/20 train/validation/test splits across three seeds. Within each author or user, we use a 70/30 profile-query split: chronological for WildChat and seeded random for PAN. Unless stated otherwise, reported experimental metrics are means with sample standard deviations over the three seeds. We train contrastive bi-encoders on four transformer backbones (DistilBERT, BERT-base, MiniLM-L6 and ELECTRA-base) under two training regimes: random-only and a 50/30/20 random/semi-hard/hard mix. We also run a secondary SBERT hardness-mining ablation on DistilBERT and BERT to test whether the findings depend on the TF-IDF definition of "hard." We release the benchmark construction scripts and evaluation code so the setup can be reproduced end to end.

Threat Model
The adversary. We consider an adversary who has physical or session-level access to an LLM agent already enrolled for a legitimate user. The legitimate user has signed in at some point in the past, the agent may have access to the user's email, files, calendar, and MCP-connected tools, and the adversary is now using that same open session. The adversary's goal is to make the agent perform an action the legitimate user did not intend, such as sending a sensitive email, exfiltrating files, posting a message in the user's voice, or running a destructive shell command. The adversary types into the agent and can approve tool calls when the agent asks. This adversary maps to OWASP LLM06 (Excessive Agency) and OWASP Agentic Applications ASI03 (Identity and Privilege Abuse), as discussed in Section 1.

What the adversary knows. We give the adversary a realistic but nontrivial amount of knowledge. They may know the user's general topic distribution because they share a workplace, family, or social circle; they may know the projects, codebases, or clients the user works with; and they may attempt to mimic the user's writing style or register if they have seen the user write before. The adversary has access to neither the verifier's internal weights nor the enrolled profile stored on the device, which matches the on-device deployment setting we recommend later.

What the defender sees. The defender is the LLM agent. It holds an enrolled profile of the user's past messages and sees the new incoming text in the current session. Given the two, the verifier produces a score and a decision. The verifier applies a fixed threshold, selected on validation data before deployment, to every incoming message after that. The verifier does not get OS-level signals such as keystroke dynamics, mouse movement, or window focus; it only sees the text the user has typed. This deliberately keeps the defense at the agent layer rather than relying on lower-layer biometrics that may not be available in every deployment.

Defended actions. The verifier does not have to turn every verdict into a hard accept or reject. It can require re-authentication for high-trust actions such as sending email or running shell commands, while still allowing low-trust actions such as answering a factual question. It can also slow the adversary long enough for higher layers, such as session expiry, OS lock or MFA challenge, to engage. We treat the verifier as one layer in a defense-in-depth stack, not as a replacement for OS-level authentication. The concrete policy mapping is given in the Deployment Recommendations section.

Out of scope. We do not study adversaries with direct access to the verifier weights who can run gradient-based attacks, adversaries who have stolen the enrolled profile from the device, or adversaries who use another LLM to rewrite their messages in the user's style using examples of the user's writing. In the second case, the on-device deployment assumption is already broken. The LLM-assisted mimicry setting is a natural next step for follow-up work and is discussed in the limitations.

Related Work
Authorship verification. Authorship verification has a long history in stylometry and the PAN evaluation campaigns have driven much of the modern work on it (Stamatatos, 2009; Bevendorff et al., 2020). The classical recipe combines character and word n-grams with shallow classifiers, and character n-grams in particular are known to mix style and topic signals in ways that can flatter same-topic evaluations (Sapkota et al., 2015), which is one of the things we explicitly stress-test against in this paper. More recent work has moved to neural encoders, Boenninghoff et al. (2019) train siamese LSTM-based encoders for the PAN cross-domain AV task, Barlas and Stamatatos (2020) compare BERT-style encoders against classical baselines, and Tyo et al. (2022) survey the broader state of the art across many backbones and datasets. Our contribution relative to this literature is two fold, we restructure PAN-20 from its native pairwise format into per-author profiles so that the task matches the deployment setting where an agent has an enrolled user history rather than two unrelated texts, and we stress-test the encoders against topic-similar imposters mined by an identity-agnostic similarity function instead of reporting only on the random or natural test distribution.

Contrastive learning and hard-negative mining. The bi-encoder with triplet loss recipe we use is standard in sentence representation learning (Reimers and Gurevych, 2019; Gao et al., 2021) and in the broader contrastive metric-learning literature (Schroff et al., 2015). Hard-negative mining is well studied in dense retrieval (Xiong et al., 2021; Robinson et al., 2021) and in face recognition (Schroff et al., 2015), where uniformly random negatives are known to saturate the loss early and semi-hard or hard negatives are needed to learn discriminative representations. We apply the same idea to authorship verification specifically and evaluate the effect not just on threshold-free metrics like ROC-AUC but on the security operating points (TAR@FAR=1%, FAR@FRR=1%, catch@3 and median messages-to-detect) that a real agent deployment would care about, which is where most of the gains from hardness-aware training actually land.

LLM agent identity and security. The risk we attack is named in OWASP LLM Top 10 (2025) under LLM06: Excessive Agency and in OWASP Agentic Top 10 (2026) under ASI03: Identity and Privilege Abuse, is consistent with MITRE ATT&CK's Impersonation tactic (T1656), and is covered by NIST AI 100-1's emphasis on accountability and governance for AI systems that take consequential actions. These frameworks identify the gap but do not come with a published empirical evaluation of whether the gap can be closed from user text alone at the agent layer, which is the gap our paper tries to fill.

Concurrent work. In concurrent work, Shen et al. (2026, WWW) study dialogue attribution in unauthenticated human-LLM sessions on the same WildChat data using a profile-induced session classifier with utterance-level matching. Our work and theirs are complementary but differ in three places. We frame the problem as a security primitive with operating-point metrics (TAR@FAR=1%, FAR@FRR=1%, catch@3) rather than dialogue-level accuracy, we add a hardness-stratified evaluation against topic-similar imposters so that the random-versus-hard robustness gap is observable, and we study a hardness-aware training regime alongside the random-trained baseline which lets us measure whether the topic-vs-style shortcut is fixable through training rather than just diagnosed. The two papers reaching the same conclusion from different angles is, in our view, a positive signal for the area.

Dataset
We use two complementary datasets. WildChat-1M (Zhao et al., 2024) is our primary dataset because it consists of real user-ChatGPT interactions and best matches the agent-chat setting we study. PAN-20 is our secondary dataset because it is a widely used PAN authorship-verification benchmark and gives us a sanity check against the established authorship-verification literature. The two datasets also differ sharply in style: PAN authors write long narrative fanfiction, while WildChat users often write shorter conversational prompts asking for code help, drafting, or advice. Using both lets us test whether our findings hold across long-form literary text and short conversational text.

WildChat-1M. We use the AllenAI release and filter to English-language users only, using the dataset's provided language field without re-detecting language; mixing languages would allow a verifier to exploit language ID rather than writing style. We use the `hashed_ip` field as a proxy user identifier, following the dataset metadata. This is imperfect: shared-IP households can merge multiple people into one identity, while a single user moving across networks can be split into multiple identities. We discuss this caveat further in the limitations. Conversations contain user turns, LLM responses, timestamps, language labels, and other metadata, but the model only ever sees raw user text. After filtering to English users with at least 10 user messages, we obtain 16,467 eligible users. Compared with PAN, WildChat is closer to the deployment setting we care about: users write short conversational prompts to an LLM, often about overlapping tasks such as coding, drafting, and advice, which makes topic-similar imposter evaluation especially important.

PAN-20. The official PAN-20 training release is distributed in pairwise format (two texts with same/different-author labels), which does not match the deployment setting we study. We restructure it by grouping every text by its author identifier across all pairs and treating each author as a single identity. After applying the same >=10-text filter we obtain 8,483 eligible authors. PAN authors write fanfiction across multiple fandoms (Harry Potter, Marvel, Star Wars and so on); we do not use fandom as a model input and do not split on it, as discussed in the methodology section. PAN texts are also much longer than WildChat messages, with a mean of roughly 21,000 characters per text, which is fine for the TF-IDF miner but does not fit the encoder in full; we char-truncate at 2,000 characters before tokenization, a defensive cap that is not tuned.

Preprocessing. We do very little preprocessing before tokenization. We collapse repeated whitespace and strip leading/trailing whitespace, but we do not lowercase, strip punctuation, or remove special characters because punctuation habits, capitalization and quirks are exactly the stylometric signals the encoder should learn. We do not use any metadata as model input; timestamps are only used to chronologically order WildChat user messages when constructing the per-user profile/query split.

Final counts. After all filters, PAN gives a mean of 16.9 texts per author (11.4 profile, 5.5 query) and WildChat gives a mean of 47.7 messages per user (33.0 profile, 14.7 query). The 60/20/20 author-disjoint split yields 5,090 / 1,697 / 1,696 authors on PAN and 9,880 / 3,294 / 3,293 users on WildChat, identical across the three seeds because the stratified shuffle preserves bucket sizes. Table 1 reports the per-seed train/val/test counts for reproducibility.

Methodology
Profile-query construction. Each author's text pool is split into 70% profile and 30% query, where the profile represents the enrolled history the agent already has for the user and the query is the new incoming text we are testing. For PAN, which has no natural ordering, we use a stable per-(seed, author) hash to shuffle and take the first 70% as profile. For WildChat we sort the user messages chronologically by timestamp and take the first 70% as profile and the last 30% as query, matching the realistic deployment where the agent has prior conversations and the imposter case happens later. We evaluate at two prefix lengths, k=1 (the first held-out query message) and k=3 (the first three query messages averaged), to see how fast the verifier converges as more material arrives. Each author contributes one positive evaluation pair (profile vs. own held-out query) and one negative pair (profile vs. a different author's held-out query) at every prefix length, so the evaluation set is exactly balanced.

Author-disjoint stratified splits. We split authors 60/20/20 into train, validation and test with no overlap across splits. This open-set arrangement forces the model to generalize on writing style rather than memorize authors. The split is stratified by total text count per author: PAN authors are bucketed into 10-12, 13-16, 17-20 and 21+ texts, and WildChat users into 10-12, 13-16, 17-20, 21-49, 50-99, 100-499 and 500+. Each bucket is split independently using a stable per-(seed, bucket) hash, which keeps the message-count distribution comparable across the three splits and reproducible from the seed alone. We deliberately do not split on topic or fandom: holding fandom shared but authors disjoint puts the verifier in the realistic situation it actually faces (same topic, different writer), which is the only situation in which the random and hard test regimes have room to differ. The three seeds we use are 13, 21 and 42, and every reported number is the mean across the three with the sample standard deviation alongside.

Hardness mining. A "hard" imposter is a different author whose text looks similar to the anchor's under an identity-agnostic similarity function; the point is to make the negatives realistically hard rather than adversarially constructed. Mining is done at the author level. For each author A in a split we rank every other author B by cos(phi(profile_A), phi(query_B)), where phi is the similarity function. The top 5% of that ranking forms the hard bucket for A, ranks 5-30% form the semi-hard bucket, and the random bucket is uniform sampling across all other authors in the same split without similarity weighting. When we need a negative text for a triplet we sample an author from the requested bucket and then a uniformly random text from that author's pool, rather than picking the single most similar text (which would concentrate gradients on a handful of authors). The anchor's own ID is excluded to prevent self-negatives, and the similarity function only sees texts, never the author labels.

We use two similarity functions for phi. The primary miner is a TF-IDF cosine model combining character 3-5-grams and word 1-2-grams with min_df=1 (so even rare n-grams contribute, and we do not cap by max_df), word features capped at 200,000 and char features at 300,000. We fit the TF-IDF vocabulary on each split independently using the concatenated profile and query texts of every author in that split, then encode each author's concatenated profile and concatenated query as separate vectors. The secondary miner is sentence-transformers/all-MiniLM-L6-v2 used as a fixed encoder with attention-mask mean pooling and L2 normalization, and cosine in that embedding space. The SBERT miner captures semantic rather than vocabulary overlap and lets us test whether our findings depend on the specific notion of "hard". All hardness indexes are cached per (dataset, seed, split) to avoid redundant computation across models.

Contrastive bi-encoder. A single transformer backbone with shared weights encodes the anchor, positive and negative texts independently. We load each encoder from AutoModel rather than AutoModelForSequenceClassification, because the latter adds a [CLS] pooler that some pretrained checkpoints initialize near zero and fine-tuning through that bottleneck collapses representations; we discovered this during preliminary experiments and document it in the appendix. For every text we mean-pool the last hidden state weighted by the attention mask and L2-normalize the pooled vector. We add no projection head, no custom special tokens and no prefix prompts, and use the stock tokenizer with max_length=256 and truncation enabled.

Training objective. We train with triplet margin loss in Euclidean space with margin 0.3. Because all embeddings are L2-normalized, the squared Euclidean distance between two embeddings is 2 - 2 cos(a,b), so minimizing the triplet loss is equivalent to pushing the anchor-positive cosine above the anchor-negative cosine by the margin, which aligns the training objective with the cosine-based scoring used at evaluation. We do not use in-batch negatives or InfoNCE; each triplet contributes its own explicit negative, which keeps the fraction of hard negatives a property of the sampler rather than the batch and makes the negative-composition manipulation that this paper studies cleaner. Triplets are resampled every epoch with a per-epoch seed derived from the run seed plus the epoch number, even though the underlying author pool stays the same.

Two training regimes. We compare two ways of choosing the training negatives: (i) random-only, with 100% random negatives drawn uniformly from other authors in the training split; and (ii) mixed, with 50% random, 30% semi-hard and 20% hard negatives. The mixed proportions match the realistic mixed test composition by design, because we want the training distribution to look like the deployment distribution where some imposters clearly differ and others try to mimic the user. The two regimes differ only in negative composition; everything else (model, data, hyperparameters, number of triplets per epoch) is held fixed, which lets us attribute any difference in test performance specifically to the negative composition.

Test protocol and scoring. At test time each profile text is encoded independently, the per-text embeddings are averaged and re-L2-normalized to give one profile embedding per author, and the same is done for the query at each prefix length to give one query embedding per (author, prefix). The verification score is the cosine similarity between profile and query linearly mapped to [0,1] via (cos+1)/2, which is monotonic in cosine and so preserves rank-based metrics like ROC-AUC and EER while keeping the threshold in a familiar range. The decision threshold is selected once on validation predictions by maximising F1 and the same threshold is applied across all four test regimes. We evaluate every trained model on four imposter regimes: random (100% random imposters), semi-hard (100% from the 5-30% similarity bucket), hard (100% from the top 5% bucket), and mixed (50/30/20 random/semi-hard/hard, the realistic deployment composition). The positives are identical across regimes so any difference is attributable to imposter hardness, and the robustness gap (random AUC minus hard AUC) for each training regime falls out directly.

Cross-miner ablation. To check that our findings are not an artifact of the TF-IDF definition of "hard", we run a secondary SBERT-miner experiment on the two largest backbones (DistilBERT and BERT) for both datasets across all three seeds, in three configurations: (a) random-only training evaluated against SBERT-mined imposters (does a model trained without hardness exposure cope with a different notion of hardness?), (b) mixed training where train negatives come from TF-IDF but test imposters come from SBERT (the cross-miner generalization test), and (c) mixed training where both train and test negatives come from SBERT (the same-miner upper bound). MiniLM and ELECTRA are not run in the SBERT ablation in this pass because (a) compact-encoder and (b) base-encoder references are already covered by DistilBERT and BERT.

Experimental Setup
Models. We evaluate four pre-trained transformer backbones in the TF-IDF hardness regime: DistilBERT-base-uncased (66M parameters), BERT-base-uncased (110M), MiniLM-L6 (sentence-transformers/all-MiniLM-L6-v2, 22M) and ELECTRA-base-discriminator (110M). The four encoders span the compact-to-base size range that fits within our 8 GB VRAM constraint. The SBERT cross-miner ablation is restricted to DistilBERT and BERT.

Hyperparameters. Triplets per author per epoch are fixed at 16, which gives 81,440 triplets per epoch on the PAN train split (5,090 authors x 16) and 158,080 on the WildChat train split (9,880 users x 16). Each text is char-truncated to 2,000 characters before tokenization (a defensive cap against long PAN profiles, not stylistically tuned), tokenized with the encoder's stock tokenizer at max_length=256 with truncation. Train batch size is 16 for DistilBERT and MiniLM and 8 with gradient accumulation 2 for BERT-base and ELECTRA-base, keeping the effective batch at 16 within the 8 GB VRAM budget; eval batch size is 32 for the smaller two and 16 for the larger two. The optimizer is AdamW with learning rate 2e-5, weight decay 0.01, no warmup (the LR stays constant for all three epochs), gradient clipping at L2-norm 1.0, and FP16 mixed precision via torch.amp.GradScaler. We train for 3 epochs and select the best epoch by validation ROC-AUC. We deliberately use the mixed validation regime for both training regimes, so that both pick their best checkpoint against the same difficulty distribution and we never compare a random-trained model selected on an easy validation distribution against a mixed-trained model selected on a harder one.

Metrics. We frame the task as a security problem, so we report at operating points rather than threshold-free averages. ROC-AUC and PR-AUC are the rank-based summaries; F1 is computed at the validation-selected threshold (held fixed across the four test regimes); EER is the operating point where false-accept and false-reject rates meet. TAR@FAR=1% answers "if we are only willing to let 1 imposter in 100 slip through, what fraction of legitimate users do we accept?" and is the number a security team would actually deploy on. FAR@FRR=1% answers the symmetric question "if we are only willing to reject 1 legitimate user in 100, how many imposters slip through?". Brier score and ECE capture score calibration, which matters when the downstream policy depends on raw magnitudes. We also report the robustness gap (random metric minus hard metric) for ROC-AUC, F1, EER, TAR@FAR=1% and FAR@FRR=1%. For streaming detection we report AUC@1 and AUC@3 (per-prefix AUCs), EER@1 and EER@3, imposter catch rate at 3 messages (fraction of imposters whose 3-message score falls below threshold), genuine survival rate at 3, and the median and P90 messages-to-detect among imposters that are caught.

Hardware and runtime. All experiments were run on a single workstation with an RTX 4060 Ti (8 GB VRAM), Intel i9-13900K CPU and 31 GB system RAM; FP16 is essential to fit BERT and ELECTRA. Hardness mining is amortized (built once per dataset/seed/split and reused), so the dominant cost is contrastive training: roughly 2-3 hours per (dataset, model, regime, seed) cell including evaluation on all four test regimes. The full 4 model x 2 dataset x 2 regime x 3 seed grid is 48 cells, and the SBERT ablation adds 2 models x 2 datasets x 3 configurations x 3 seeds = 36 more, for 84 result files per pass.

Statistical reporting and reproducibility. Every reported number is the mean across the three data seeds (13, 21, 42) with the sample standard deviation alongside. Seeds control author/user assignment to splits, model weight initialization, and triplet sampling. We do not sweep hyperparameters across the full grid: the per-model-class hyperparameters above are selected by the 8 GB VRAM constraint and held fixed across all model/dataset/regime/seed combinations. We seed Python's random, NumPy and Torch (CPU and CUDA) at the start of every run; CUDA kernel determinism is left off in exchange for the speed-up. All intermediate artifacts (split assignments, hardness indexes, model checkpoints and prediction tables) are written to disk so the pipeline can be resumed at any stage. We will release the source code, preprocessing and split-generation scripts, experiment configs, evaluation code and result JSONs under an open-source license. The raw and processed text files are not redistributed because both datasets contain user-sensitive content; users can reconstruct the splits deterministically from the released seeds and scripts against their own dataset downloads.

Results
All numbers are mean +/- sample standard deviation over seeds 13, 21 and 42. Tables 2 and 3 give the full per-encoder breakdown on PAN and WildChat, Table 4 gives the random-to-hard robustness gap per encoder, and Table 5 gives the SBERT cross-miner ablation on DistilBERT and BERT.

The encoders work on random imposters but break on topic-similar ones. Across all four encoders the random-imposter test regime is essentially solved: ROC-AUC sits between 0.95 and 0.97 on both datasets under either training regime, and TAR@FAR=1% on WildChat random reaches 59-63% for the stronger encoders. The hard regime is a very different story. Under random-only training, ROC-AUC drops from 0.96-0.97 random to 0.85-0.89 hard on WildChat (9.85 points for BERT, 9.54 for DistilBERT, 10.63 for ELECTRA, 7.55 for MiniLM), and TAR@FAR=1% on WildChat Hard collapses to 6.2% (BERT), 7.3% (DistilBERT), 4.3% (ELECTRA) and 21.7% (MiniLM, which had a stronger pretrained representation to start with). On PAN the drops are smaller (2.9 ROC-AUC points for BERT, 3.4 for DistilBERT, 2.9 for ELECTRA, 3.6 for MiniLM), which is consistent with PAN texts being long and content-rich enough that the encoder has more style signal to fall back on, but the gap is present on every encoder. This is the topic-vs-style failure mode we set out to expose.

Hardness-aware training closes most of the WildChat gap. Switching the training negatives to the 50/30/20 mix shrinks the WildChat random-to-hard ROC-AUC gap from 9.85 to 6.51 points on BERT (a 34% reduction), 9.54 to 6.78 on DistilBERT (29%), 10.63 to 8.23 on ELECTRA (23%), and 7.55 to 5.85 on MiniLM (22%). The PR-AUC gap on WildChat shrinks even more sharply, from 13.84 to 7.56 on BERT and from 12.88 to 7.91 on DistilBERT, roughly halving. The biggest absolute gain lands on TAR@FAR=1% on WildChat Hard, which is the metric a security team would actually deploy on: 6.2% -> 22.3% for BERT (+16.2 points) and 7.3% -> 20.3% for DistilBERT (+12.9 points), with the corresponding WildChat Mixed-test TAR@FAR=1% climbing 18.9% -> 42.2% for BERT and 22.3% -> 41.9% for DistilBERT. PAN gains are smaller (+2 to +3 TAR@FAR=1% on hard), which is expected given the small PAN baseline gap. The takeaway is that hardness-aware training matters most where the gap is large, which is exactly the deployment-realistic WildChat data.

Streaming detection helps further. When the verifier sees three query messages instead of one, the imposter catch rate on WildChat Hard rises to 69% for BERT mixed and 69% for DistilBERT mixed (up from 65% under random-only training), and the median messages-to-detect on imposters that are caught is one across all four encoders and both datasets. So in the cases where the verifier does flag the imposter, it flags them on the first message itself. On the more realistic WildChat mixed-test distribution, catch@3 sits at 85% (BERT mixed) and 85% (DistilBERT mixed), meaning the agent intercepts roughly five out of six imposters within the first three turns of a session, which is the operating regime a deployment would actually see.

The SBERT cross-miner ablation reproduces the direction. Swapping the test imposters from TF-IDF to SBERT-mined drops the WildChat Hard ROC-AUC by about 4 points for the TF-IDF-trained model (BERT 89.76 -> 85.95, DistilBERT 89.60 -> 85.75), which tells us SBERT produces a different and slightly harder slice of hard imposters than TF-IDF. Training on SBERT negatives at training time (the same-miner upper bound) recovers most of this, reaching ROC-AUC 86.43 on BERT and 86.60 on DistilBERT on WildChat Hard. Importantly the topic-vs-style gap and the hardness-aware fix both replicate under SBERT mining: WildChat Hard TAR@FAR=1% under SBERT evaluation goes from 5.2% (random-only) to 18.3% (BERT, SBERT mixed) and from 7.4% to 20.3% (DistilBERT, SBERT mixed), so our finding is not an artifact of how we define "hard". On PAN the SBERT cross-miner numbers are within noise of the TF-IDF numbers, which is consistent with PAN being a much less hardness-sensitive dataset.

What this means for deployment. Even after hardness-aware training, the strongest configuration accepts only about one in five legitimate users at FAR=1% on the WildChat Hard regime, which is not enough for the verifier to gate medium-trust actions on its own. This is exactly why the Deployment Recommendations section describes a tiered policy where the verifier runs silently on low-trust actions, contributes one click of friction on medium-trust actions, and is one of several layers (not the only one) on high-trust actions. The contribution of this paper is not a verifier that solves the problem end to end, it is a calibrated measurement of how far a text-only verifier gets at the agent layer today, and a recipe for closing the topic-vs-style shortcut that was the largest blocker against realistic imposters.

Deployment Recommendations
The numbers in this paper say the verifier is not strong enough to be a deployment's only line of defense, but it is useful as one layer when combined with the controls OWASP already recommends for LLM06. We translate the operating-point numbers into concrete agent-side policies a real deployment could implement on day one.

Action categories. Following OWASP LLM06's emphasis on minimizing agency and requiring human approval for high-impact actions, we organize agent actions by consequence into three deployment tiers. Low-trust actions are reads and short responses that do not change persistent state (answering a factual question, looking up a calendar entry, fetching a public URL) and a wrong verdict is recoverable in both directions. Medium-trust actions change persistent state in ways that are visible and recoverable (drafting an email but not sending, creating a calendar event, editing a file in the user's workspace, committing code that has not been pushed). High-trust actions are the ones an imposter would actually want and the ones that carry incident-level risk (sending email, transferring funds, running shell commands, modifying access tokens, posting publicly in the user's voice, or calling an MCP tool that touches an external system the user does not also control).

Where the verifier helps. Our mixed-regime BERT on WildChat reaches TAR@FAR=1% of 22.3% on the Hard imposter test (DistilBERT 20.3%), meaning at a 1% false-accept budget we accept about one in five legitimate users. On the Mixed test, which is our closest deployment-like distribution, the same model reaches TAR@FAR=1% of 42.2%, accepting about two in five legitimate users. Streaming helps further: imposter catch rate at three messages is 69% on the WildChat Hard regime for DistilBERT mixed, and the median messages-to-detect on the same regime is one. The verifier is not a perfect gate but it rejects the majority of imposters within three messages.

Suggested policy. For low-trust actions run the verifier silently and log the score for telemetry, do not block. For medium-trust actions run the verifier at the FAR=1% operating point and require a single click of in-app confirmation when the score falls below threshold (the failure mode is "user clicks confirm again" which is annoying but does not break anything). For high-trust actions do not rely on the verifier alone, require a fresh OS-level authentication (biometric, password, hardware token), a re-enrollment of the agent session, or a delay that gives session-expiry and screen-lock layers time to fire. The verifier's role at this tier is to flag the session for review and raise the friction the legitimate user has to clear, not to make the trust call by itself. Because the verifier scores every incoming message, a rolling three-message monitor can escalate the next medium-trust action to high-trust treatment if the score drops below threshold mid-session.

What the deployment does not get for free. At the strict 1% false-accept budget on hard imposters the verifier rejects roughly 80% of legitimate-user attempts, which is too friction-heavy to gate medium-trust actions on its own. The policy above explicitly avoids relying on the verifier as a sole gate above low-trust. We expect adaptive thresholds, longer enrollment profiles, and combining text-based verification with behavioral biometrics to lift the operating-point numbers high enough for medium-trust gating in follow-up work. The present numbers are sufficient for the verifier to be a defense-in-depth layer today, not the only layer.

Conclusion
We have studied whether a text encoder can act as an agent-layer identity check for LLM-driven desktop agents, on a profile-query authorship verification benchmark built from WildChat-1M and a regrouped PAN-20. Off-the-shelf contrastive bi-encoders look strong on the random-imposter regime (ROC-AUC above 0.95 on both datasets, TAR@FAR=1% above 60% on WildChat random for the stronger encoders) but rely heavily on topic and vocabulary rather than writing style. The moment the imposter shares topic with the genuine user, WildChat ROC-AUC drops by about 10 points across all four encoders and TAR@FAR=1% collapses into the single-digit percentages for BERT, DistilBERT and ELECTRA, which is the operating point a real deployment would care about. This topic-vs-style gap is the empirical centerpiece of the paper.

Training with a 50/30/20 mix of random, semi-hard and hard imposters mined by an identity-agnostic TF-IDF similarity closes most of this gap on WildChat and a substantial part of it on PAN, with the largest absolute improvements landing on the security operating points (TAR@FAR=1% on WildChat Hard rising from 6-7% to 20-22% for BERT and DistilBERT) rather than on threshold-free averages. The improvement direction holds under a secondary SBERT cross-miner ablation as well, so the finding is not an artifact of the specific definition of "hard". The absolute numbers are still not strong enough for the verifier to be a deployment's only line of defense, at the strict FAR=1% budget on hard imposters it rejects roughly 80% of legitimate users, so we recommend deploying it as one layer in the tiered policy described in the Deployment Recommendations section, where the verifier silently scores low-trust actions, adds a single click of friction on medium-trust actions, and is one of several layers on high-trust actions.

We see three follow-up directions. First, a stronger adversary model where the imposter uses an LLM to actively rewrite messages in the user's style after reading some of the profile, our current dataset uses real topic-similar authors as imposters, not adversarial mimics. Second, longer enrollment profiles combined with behavioral signals (keystroke timing, action patterns) to push TAR@FAR=1% high enough for the verifier to gate medium-trust actions on its own. And third, scaling to larger encoders than our 8 GB VRAM budget allowed and to multilingual settings beyond English. We release the benchmark construction scripts and evaluation code so all three follow-ups can be reproduced from the same setup.


Limitations :
    In order to identify users in WildChat we use the hashed_ip field, but this is imperfect because it suffers from the shared IP problem and single user moving between networks can contribute multiple identities. We accept these caveats since the dataset is large enough that we expect some noise to be diluted when we aggregate at scale, but on a real deployment environment we need a more reliable identity signal than IP addresses.
    Our results don't say anything about multilingual authorship verification or the case where an imposter can use a different language than the user or in some scenarios the same author may use different languages while communicating with the LLM. In WildChat we filter the dataset to English language users only so the verifier does not win the task just by detecting language ID instead of the writing style.
    The hard imposters in our datasets are real authors or normal users and not humans with malicious intent. A real adversary trying to impersonate a user will probably do something similar by matching topics or vocabulary of a legitimate user but we do not test the stronger cases where the adversary is trying to replicate the user's style to gain access.
    All experiments were run on a single 8 GB GPU which limits us to models under 200 M parameters at our sequence length. We evaluate on four encoders DistilBERT, BERT-base, MiniLM-L6 and ELECTRA-base and the SBERT cross miner ablation is run only on two of these encoders. We couldn't test larger encoders so whether the robustness gap closes at scale is not something we can verify given the hardware limitations.
    WildChat dataset was collected in the early days when LLMs were just released and the conversations it contains are mostly around user seeking help to write code or debug something. It doesn't contain the chats where users ask an LLM to perform operations while interacting with the MCP servers, where the LLM can have access to delete files, read emails or access user's personal accounts. So in a real deployment the threat model is much sharper than what we study as part of this experiment because the imposter who gets access to the LLM can cause real damage. Related to this, we currently do not study the risk scores of the imposter messages to determine how dangerous an imposter would be if accepted and that is something we plan to include in follow-up work.

Ethics :
    Authorship verification is double-edged sword, the techniques that we study to refuse imposter sessions inside LLM agents can also be used to link anonymous online writing back to real people with known writings which will be disastrous for some users like whistleblowers, journalists and activists who depend on the right of anonymous speech. We did not invent the underlying techniques but we want to be explicit that any deployment of this verifier outside the LLM-agent settings should be scrutinized carefully.
    Beyond this, we recommend that the deployments run on a user's on-premises device and the enrolled profiles themselves should not be sent to a central server or stored online at all. Moving user profiles in a remote backend database even for legitimate purposes of running verification can create aggregated dataset on how an individual writes and this kind of dataset can become a target for both insider misuse and for external attacks. Keeping the verifier on the user's device with the profile is a comparatively safer default because the writing style stays with the user.
    PAN-20 dataset is distributed under a research license and WildChat-1M is distributed under the license terms listed with the AllenAI release and we follow the terms of the exact dataset artifact used. Both the datasets may contain sensitive content related to the users in their texts so we do not redistribute the texts and do not release any model checkpoint that is fine-tuned on the individual user data. During training or evaluation the model never sees the user metadata fields such as hashed_ip, country, conversation_id etc. it just sees the user texts.
    When the verifier is deployed inside an LLM agent the cost of being wrong by accepting an imposter and by rejecting a legitimate user is not the same. If the verifier wrongly accepts an imposter that becomes a greater security risk as the imposter can get the agent to send an email, access a file or run a command. If the verifier on the other hand wrongly rejects the legitimate user they may just have to relogin to get the access which is annoying but recoverable. So we operate in a strict setting where our encoders keep out imposters even if it means rejecting some legitimate users. Some models on hard test regimes accepts only about a half of the legitimate users when the imposter accept rate is down to 1 in 100. This is not strong enough for the verifier to be the only defense so we treat it as another layer that sits on top of OS-level login and per-action approval and it doesn't act as a replacement for them.
